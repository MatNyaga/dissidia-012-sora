## In plain words (for Mat)

- **Goal.** Today Sora is built into the game by old one-off scripts. After P2.8, Sora is just a "package" that a
  general installer puts on top of the engine, the same way the test fighter (and later Riku or anyone) will go on.
  The installer does not know Sora's name or number.
- **What I checked.** I took the tested engine disc (P23-flags, the one that already works like the release on
  PPSSPP and your Vita) and sorted every changed instruction into "engine", "made from Sora's registry file" or "still
  Sora-only code". Everything made from the registry file is predicted by our tools and matches the disc exactly.
- **The engine part is generic**, with one catch: 143 of its instructions exist today only inside Sora's old patches
  (they were written for Sora, but they work for anyone). The engine tools expect them to be there already. So the
  first build step is to make a real "engine package" that carries them itself, built from the clean game.
- **Two pieces of Sora-only code are still left**: the save-record code (P2.5) and the title-screen voice call
  (P2.7). Until those tasks land, the Sora package keeps them as "transitional" patches. The installer still treats
  them as plain package data; it does not know what they are.
- **The "merge gap" is real and bigger than first thought.** Sora's package stores many edits as "change these bytes
  at this position", including the counters and the lists of positions inside the game files. A second fighter would
  need to change the same counters → clash. It also stores new rows by their final position, and a second fighter can
  shift those positions (shown with the model list: the test fighter's rows would push Sora's three rows down by 3).
- **The fix:** store each edit by *what it is* (owner number, text entry number, model id, picture id), and let the
  installer recompute every counter, position and gap filler from the clean game plus all packages. I wrote and
  tested this for most of the affected tables: rebuilt from the clean game, Sora's tables come out **byte-for-byte**
  like the released disc (82 checks pass), and adding a pretend second fighter leaves Sora's parts untouched.
- **What you would decide** (§7): whether the menu-speed fix (menus at 333 MHz) belongs to the engine for everyone,
  and whether it is OK that, once two fighters share a menu file, ten files are re-packed slightly differently
  (same pictures/texts, different padding).
- Nothing was built, run or published. The plan in §6 says which test discs a later helper makes and what to test.

### 2.2 Fighter package `sora` (format 1.1)

- `registry.json` = today's `tools/dlc/registry/sora.json` (row, behaviours, items, flags, install.*), moved into the
  package and listed in the manifest (`"registry": "registry.json"`; answers rowgen Q-RG1). `features` with
  `transitional_patches` goes away (the registry is the one source).
- `files/`: 179 PACKAGE files (162 + 10 fighter files `*sev120*`, 5 Museum icon files, 2 battle files) + 3 BGM AT3.
  `eboot_plain` moves to the engine package.
- `rows/`: re-keyed with the codecs of §3 (identity keys). Dropped: the 17 `img:` rows of rowgen tables (generated)
  and the 1,356 empty picture fillers (derived). Kept: 10 layout pins, marked "sole editor only" (§3.4).
- `patches/`: only `save_record_hooks` (121 words, minus the 2 card-cap words rowgen writes) and `title_call` (155
  words), with `set: transitional` and an exclusive claim (a second package touching them = error). They retire with
  P2.5 / P2.7 (steps E4 / E5).
  **Update 2026-10-22: both are retired.** P2.5 made the save records engine code and P2.7 generates the title call,
  so `packages/sora-C` carries no game-code patches at all ([P2.8-build.md](P2.8-build.md) §2).
- `allocations`: as today minus `code_cave` (sound banks 219000 / 219100 / 219500 / 219600, voice lines, item ids
  678–681, BGM ids 131–133, Museum icons 414–417, objentry ids 1457–1459 + reused rows, picture numbers, name_index
  63, record slot 24, flags). Reused vanilla ids are declared (`role: reused_rows`, flags `reuse_vanilla`) instead of
  registry.py's `GRANDFATHERED = {'sora'}`.
- `requires: [{"id": "engine", "version": ">=2.5.0"}]`.

### 2.4 Install order (generic; `p28_plan.py plan` prints it with counts)

1. CLEAN sha256 = df94177d…; OUT must not exist (install.py already does this); packages sorted by `requires` /
   `install_after`, ties by id → engine first.
2. produce `eboot_plain` (engine package).
3. engine base patch set (820 words, guard old = clean).
4. package patches (today: Sora's 2 transitional files, guard old = clean).
5. roster-wide generated code-image data: rowgen + OXT + panel_tex (guard: the clean words; refuse on rowgen refusals).
6. container rows of all packages, per node, through the codecs (§3): counts, offsets, final indexes, fillers derived.
7. whole files (PACKAGE + ISO).
8. EXTRA.REG (roster), EXTRA.PRX (engine package), EXTRA.IDX (all PACKAGE files), directory records, PVD.
9. self-check: every produced file read back (install.py `self_check`), then `.part` → OUT.

### 2.5 How the installer stays generic
- Inputs: package manifests, their `registry.json`, owner_tables.json specs. The installer never compares an owner
  with a number; owner limits (33..34) come from owner_tables / registry.py rules.
- Owner-specific knowledge is data: registry rows (EXTRA.REG), allocations, codec keys.
- Gates (every build): `p28_plan.py leftovers` (0 unreviewed), `owner_scan.py --disc` (owner-33 compares 0; other owner immediates
  0 once E4 lands), `grep -n "0x21\|\b33\b\|sora" tools/pkg/install.py` = 0 behaviour hits.

### 2.6 Rollback / uninstall
- The installer never changes a disc in place: every roster is a new ISO built from the player's clean ISO
  (install.py: OUT must not exist, writes OUT.part, renames after the self-check). "Uninstall Sora" = rebuild with the
  remaining packages; "uninstall everything" = the clean ISO the player already has. The release app does the same
  with deltas against the clean ISO (P2.11 decision b).
- Saves: removing a pack keeps its record in its slot until a new friend card lands there (P2.5 §A); an engine-only
  disc reads old Sora saves like vanilla reads them (shared blank record; **unverified at runtime**).
- Dev discs: the in-place `--rollback` of install_engine / p24_stubs / p23_* stays for oracle-based test discs only.

## 3. The merge gap and how it closes

### 3.1 Classes (`p28_plan.py package`, rows of packages/sora-R4)
| class | rows | what goes wrong with two packages | fix |
|---|---|---|---|
| G1 bytes leaf | 540 | byte offsets of the clean node, including count bytes and offset tables (acab `at 8: 21 → 22`, text groups `delete at 0` + `replace at 4`) → both packages edit the same keys | identity-keyed codecs: `odir`, `acab`, `text` (built), `seco`, string tables (to build) |
| G2 grid add | 105 | add rows keyed by the **final** index; another package's rows shift them | key = id (sorted tables) / allocated id (positional tables) / (owner, k) (append lists) |
| G3 pak filler | 1,356 | size-0 entries that keep picture ids contiguous: both packages ship the same filler ids | derived by the installer (`pak_join` needs contiguous ids) |
| G4 layout pin | 10 | pin guard = the canonical skeleton of one package's member list | sole-editor only; else canonical re-encode |
| G5 img: data | 17 | data in code images at owner-33 slots | generated roster-wide (rowgen), not stored |
| OK | 62 | member add/replace by name, grid replace/patch by clean index | — |

### 3.2 Proof (`p28_codecs.py prove`, 82/82 PASS, ~3 s)
- **odir.v1** (amas, chrl): clean + `{owner 33: Sora's list}` re-encodes to the oracle bytes (amas 38 entries, chrl
  52; 1 keyed row instead of 33 byte rows each). Format confirmed: header 16 B (count @8), rows sorted by owner, clean
  data region kept verbatim, Sora's list appended (tail 304 / 416 B).
- **acab.v1**: Sora = "share owner 13's list" (entry (33, 49, 2832)); 1 keyed row instead of 34.
- **text.v1**: 29 text groups (28 u16 + the OFF4 group `mess_pk_customize_ability_0 #1`, 2,604 → 2,672 entries):
  entry-keyed rows (plain text, XOR from the final index) reproduce every group. `customize_ability #0` = 377 vanilla
  placeholder entries ("WOL 15" …) replaced → a global `text_index` allocation, composable.
- **grid-id** (ablt u16 id, objentry s16 id, both sorted, binary-searched): reproduces the oracle; with synthetic
  owner-34 rows Sora's objentry rows move from final 1170..1172 to 1173..1175 → final-index keys cannot compose.
- **pak-fill**: 16 picture packs; 12 reproduce byte-for-byte with derived fillers; the 4 pinned ones have equal
  entries and differ only in history filler bytes.
- Each family also composes a synthetic owner-34 entry with Sora's unchanged and order-independent results.

### 3.3 Not proven yet (format unverified, step E2)
- `brai.0` seco (15 rows): tables with own counts, brain sets 200..207, owner list 0x1A8 + matrix 0x1C0
  (`tools/scripts/spot33_ai.py` seco_parse / FIELDS) → `seco.v1` keyed by (table, owner) / set id; internal row
  references (0x24 first index) relocated at install.
- String tables `main_lang ability.bin / item.bin / item_help.bin / bgm_name.bin`, `field_lang battle_voice_name.bin`
  (111 rows), `manual_param.bin`, `command_list_param.bin`, `update_list_param.bin`, `assist.bin` → per format
  (scripts: ability_text.py, voice_text.py, spot33_tips.py, spot33_cmdlist.py, spot33_catalog.py, spot33_assist.py).
- Positional grid spaces (bgm_entry index = BGM id 131–133, item index = id − 1 for 678–681, uicn 413–416, jobp 10,
  collection_param sections, eqpm 34 = preset 250): keys = allocated ids; **open:** what fills a gap when a package
  that owns lower ids is absent (inert filler row per table, or the allocation must be dense — runtime question).
- VOLD lists (60 adds, one per other fighter): append per (owner, k) in owner order; **open:** whether row order
  inside a list changes which line plays.

### 3.4 Layout pins
10 pins (text: update_list, chara_select, story_mode, loading, network, exmode; menu: lpk_customize, lpk_exmode,
lpk_shop, pk_exmode). Rule: a pin applies only when its package is the only editor of that container; otherwise the
installer re-encodes canonically and reports it. Sora-only discs stay byte-identical to the oracle.
