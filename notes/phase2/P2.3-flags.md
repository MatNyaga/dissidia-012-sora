## In plain words (for Mat)
- The Jukebox hides fighter-pack music and voices until you buy them, even on a "100 %" save that lists everything.
  Before, three places in the Jukebox code had Sora's flag numbers written in. Now they ask one small helper "is this
  a fighter-pack purchase flag?", and the answer comes from the fighter pack's registry file (a short list of flag
  ranges instead of one big bitmap). Same result: on Mat's 100 % save the KH2 tracks stay hidden until bought, and
  Sora's voices show exactly as before.
- In the Labyrinth, a battle against Sora used to get the stage music when his own KH2 tracks were not bought yet
  (else silence). That rule said "fighter 33"; now it says "a fighter with a registry row". Same music.
- **With this step no "fighter 33" check is left in the P2.3 code** (owner-33 compare count 0). The last owner-33 numbers on the
  disc belong to the save code (P2.5).
- Without our module (or without its registry file) nothing breaks: the Jukebox then lists the unbought KH2 tracks
  (like the original 1.0 before the fix) and the Labyrinth fallback is off — the planned "degraded" look.

## 2. EXTRA.REG flag-range list (registry.py + module, engine 2.5.0)
- **Format:** header +0x20 `u32 franges_off`, +0x24 `u16 frange_count`, +0x26 `u16 0` (was flag_lo / flag_bits);
  entries `u32 lo | count << 16` = runs of consecutive gate flags, sorted, non-overlapping, count ≥ 1, lo + count ≤
  5120, at most 16 (`FRANGE_MAX`). Built from the sources' `gate: true` flags (`flag_ranges()`).
  **MIN_ENGINE 0x00020500**: a 2.4.x module would read +0x24 as a bitmap range. registry.py reads pre-2.5 files the old
  way (min engine < 2.5.0 → bitmap), so `install_engine.py` still accepts the frozen P2.4 recipes' EXTRA.REG files
  (P24-items rebuilds 807e09fc…).
- Sizes: sora 3 ranges = 12 B (was a 383-bit map, 48 B) → EXTRA.REG 288 B (was 324); sora + test34 4 ranges
  ((888,2) (925,1) (1263,8) (3200,1)) → 364 B (was 536: the one-range bitmap spanned 888..3200).
- **Module 2.5.0** (`extra/v2.c`): validates the list (bad → reg_state −8, first_bad 0xC0000 | index, nothing
  published), copies it to `g_franges[16]` (16-aligned .bss), publishes **FLAG_PTR (XSTB REG +0x20 = 0x089A8B44) then
  FLAG_N (+0x24 = 0x089A8B48)** after REG_PTR and before REG_COUNT, clears both in `module_stop`. Status +0xAC
  `flag_ranges` = ranges | total flags << 16 (sora 0x000A0003). The REG block word +0x24 means FLAG_N from 2.5.0 on
  (was "FLAG_LO|BITS", never published by 2.0-2.4).
- registry selftest +7 cases (runs, overlap, unsorted, empty run, past 5119, old header field, 17 > 16); host test v2
  +8 cases (published words + list, two rows, 4 bad lists, old-format header, 2.4.0 min engine still loads, no gate
  flags → nothing published): **87/87 PASS**; v1 14/14; v1 extra.prx e7e25242… unchanged.

## 7. Problems / lessons
- First Records-append version folded an `addiu` that was the NEXT call's argument; the mips_emu block test caught it
  (compare call arguments, not just the changed register).
- `install_engine.py` validates EXTRA.REG with the current registry rules: a format change must keep reading the
  frozen recipes' older files (min engine decides the format), or frozen recipes stop building.
- The slow machine swallows / wedges debugger connections; probes must keep breakpoint events that arrive while waiting
  for another reply (bgmprobe), and must always remove their breakpoints.
