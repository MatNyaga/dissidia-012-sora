## In plain words (for Mat)
- Sora's Trinity Limit, the Kingdom Key EX bonus and the reflect helpers are no longer hand-written game code. They
  are C code in our module now, and the space they used in the game holds the new "switchboard" (32 slots, 10 used).
- The new test disc is a copy of the frozen reference disc plus only these changes (and the generic name code from
  P2.3). A checker confirms nothing else differs. The old "is this owner 33?" tests in that code are gone.
- An offline test runs the **old** Trinity code in a tiny emulator next to the **new** C code on the same fake game
  data: every game call came out identical (12 scenarios).
- On the emulator: Cloud's and Garland's EX Bursts are normal, an incomplete Sora burst ends standing on the ground as
  before, and with the module removed Sora's burst still plays (with Cloud's Omnislash logic) instead of hanging.
- **The problem:** a FULL Sora EX Burst freezes the game in PPSSPP's normal (JIT) mode on the new disc. The same
  burst works on the reference disc, on the step-0 disc, and on the new disc in PPSSPP's slower IR mode. I narrowed it
  down to the item-effect hook (Kingdom Key bonus): with that one hook left on the old route the full burst works.
  I did not find the root cause yet. Nothing is released; the disc is a test disc.
- **Update 2026-10-21 (fixed):** the real cause was not the item hook. Our C code left the game's stack 8 bytes off
  from the 16-byte grid the game expects; when Sora's "bar full" voice played, the game copied a 3D matrix onto that
  stack with an instruction that needs the grid, and PPSSPP's fast mode got stuck retrying it. The module now lines the
  stack up before every call into the game. New test disc `dumps/ULUS10566-P24-tri2.iso`: full Sora bursts work in
  PPSSPP's normal mode (3 of 3), everything else still matches the reference disc (§8).

## 8. The JIT freeze: cause, fix, tri2 (P2.4 freeze helper, 2026-10-21)

### 8.1 Cause (found with gdb on the frozen PPSSPP)
- PPSSPP 1.20.4 (flatpak, the newest installed; no other build on this machine), own profile, port 41339, DEFAULT
  settings: P24-tri froze at 8101 in 3 of 3 runs (logs/run_base2, base3, s5van1 in dumps/screens/p24-tri2/).
- gdb can attach only from an ancestor (ptrace_scope 1): the runner shell `exec`s gdb on the frozen PID. The hot thread
  is **EmuThread inside JIT code**, not a deadlock. 20000 `stepi`: only 12 host addresses, guest registers unchanged:
  `movaps [membase + 0x09FFF448], xmm10` → PPSSPP's SIGSEGV handler → `sigreturn` → the same `movaps`, forever. The
  game never finishes a frame, so the debugger and SIGTERM never get a turn (that is why it looked like a hard hang).
- The guest store is a VFPU `sv.q` (4×4 matrix copy, game function 0x089A3FB8 called from 0x08836A0C) into a stack
  local at **sp = 0x09FFF438 (8 mod 16)**. `movaps` needs 16-byte alignment → #GP → the handler does not skip or
  report it → endless loop. The IR interpreter does sv.q as four 32-bit stores (no alignment rule) → no freeze.
- Who misaligned sp: the stack walk of the RAM dump gives FUN_08a39db4 → S1 hook 0x08A39ECC → `wrap_tri_bar`
  (sp 0x09FFF4F0, aligned) → **`beh_tri_bar` (psp-gcc frame −8)** → G_VOICE 0x0884EA08 (a1 = 0x014E521A, the bar-full
  voice 21910042) → the game's sound/3D code → matrix copy on the stack. psp-gcc's EABI keeps sp only **8-byte**
  aligned (module frames −8, −24, −72); the game's compiler keeps 16 and stores vectors/matrices on its stack with
  sv.q / lv.q. R4's hand-written TRI used 0x20-byte frames, so the oracle never had this.
- **Stub 5 is not involved:** P24-tri with FN_PTR[5] poked back to F5 (0x089C1F78, vanilla route) at battle start froze
  the same way (logs/run_s5van1.log, same fault loop and stack). The step-1 bisection (§4.4) had one full burst per
  variant and the trigger is not every burst, so "S0-S4 PASS" was luck. (Why the game takes the matrix path on some
  bursts and not others is not known; it does not matter once sp is aligned.)
- On a real PSP / the Vita a misaligned sv.q is not safe either (the VFPU quad store needs 16-byte alignment): the old
  P24-tri must never go to the Vita; tri2 should.

### 8.2 Fix (engine 2.1.1, module only — no disc word, stub or ABI change)
- tools/pkg/engine/extra/beh.c: `GFN(t, a)` now calls `gt_<address>`, one tiny asm thunk per game function (X-list
  `GAME_FNS`, 16 functions): `move v1,sp / addiu sp,-32 / and sp,~15 / save old sp + ra / jalr game / restore`. It
  leaves every EABI argument register (a0-a3, t0-t3, f12-f19) and the return values alone, clobbers only at/v1, keeps

### 8.4 Lessons + what step 2 must watch
- **Rule:** module code reaches game code only through `GFN` (aligned thunk). Asm wrappers keep 16-byte frames. New game
  functions → add to `GAME_FNS`. ENGINE.md "§10 wrapper rule", notes/dlc.md §F 15.
- **Bisection hygiene:** a freeze that does not hit every run needs ≥3 runs per variant; one PASS proves nothing.
- **Find hangs from the host side first:** gdb from the launching shell + a guest RAM / MIPS-context dump (scratch
  helper `frzdump.py` pattern: EmuThread, r14 = &mips + 0x80, rbx = membase) found in one run what a week of guest-side
  bisection could not. PPSSPP 1.20.4 bug worth knowing: an alignment fault in fastmem JIT code loops forever instead
  of showing an error (FastMemoryAccess = False avoids it; the IR interpreter never faults).
- **Step 2 (Reflect cave C1-C7 + HELM in C):** HELM runs every EX frame and takes/returns floats (f12/f13) — its C must
  not call game code except through the thunk; C1/C2 call battle-overlay code from EBOOT hooks (keep the overlay
  guard and the thunk); EE_GUARD / EE_PROJ / TRI_HPROW already go through the thunk. The reflect barrier code uses
  VFPU heavily (matrices/vectors for the dome): any vector the module passes to the game (like `g_tri_pos`) must be
  16-byte aligned in .bss/.data (`__attribute__((aligned(16)))`), never on the C stack. Test every step-2 disc with
  ≥3 full bursts + reflect uses on the JIT AND once strict, before calling it done.
- **Vita:** P24-tri must not go to the Vita (misaligned sv.q). tri2 is the first P2.4 disc that is safe to try there.
