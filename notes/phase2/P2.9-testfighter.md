## In plain words (for Mat)
- The test fighter is a copy of Cloud with a new name ("Test Fighter"), placed on the game's spare number 34 (the
  number the game gives Cosmos). It is never released. It only proves that a second extra fighter works **without
  any new fighter-specific code**.
- **It cannot be built yet.** (Status 2026-10-22: P2.3, P2.4, P2.5 and P2.7 are done and P2.8 is being built;
  see the updated table in §1.) Most of what it needs comes from Phase-2 tasks that are not done: the generic lookups
  (P2.3), save slot 23 (P2.5), the room problems (P2.7: select-grid row table, equipment presets, Records list,
  Jukebox list, Characters panel, Original Quest face list, Museum viewer list) and the engine install layout "C"
  (P2.8). It does NOT need the behaviour modules (P2.4), because the test fighter has no special moves code, except
  one thing: owner 34 shares Garland's equipment bit, so it would see Garland's own gear until P2.4's item-owner
  table covers every extra owner.
- **The Cosmos story risk is real** (found statically today). Story scenes load Cosmos by his model number, which
  is safe, but the game then picks Cosmos's extra files (`.cosx`, `.exex`) by "owner 34, costume 1". If the test
  fighter is on owner 34, Cosmos would get Cloud's extra files in story scenes. Putting the test fighter's model
  rows after Cosmos's does not help either: then the test fighter would get Cosmos's model in battle.
  A 2-byte fix (move Cosmos's rows to an unused costume number) passes the static check; it needs one emulator
  check in a Cosmos story scene.
- **Two smaller mistakes in today's placeholder** `tools/dlc/registry/test34.json`: its model ids 1300-1302 are
  already used by the game (Tifa/Kain/Garland menu models), and its unlock flag 1285 is outside the agreed package
  pool 3200-3455. The validator does not catch either yet.
- Two things can be done today without waiting: the static Cosmos check (done here, tool committed), and the P0.4
  runtime Cosmos check on a throw-away copy of the oracle (steps below).

## 3. The Cosmos story-scene risk — static answer + exact checks

### 3.1 How models are found (EBOOT, clean decompile `dumps/decomp/all.c`)
- **By id:** `FUN_088470b8(id)` → `FUN_08846c98` = bsearch over objentry (68-B rows, comparator `LAB_08846c0c`:
  it compares the s16 id at +0). → **objentry must stay sorted by id** (vanilla has 2 duplicate ids,
  5 and 188, harmless). Story/field scenes use this path: the talkevent field loader (FUN_088e897c, `talkevent/%s.evex`
  + `.fobx` object list, registered by FUN_0881e248) walks its object list (FUN_0881e75c) and loads each entry with
  FUN_088470b8 on the entry's id (per the local decompile), the same in FUN_08910b54 / FUN_08915bdc. World-map objects of type 5 carry an
  explicit model id (+0x1E, FUN_089121f4).
- **By owner:** `FUN_088470dc(owner, costume, assist)` → `FUN_08846ccc`: **first row in id order** with
  row+6 == owner (≠ 0), row+7 == costume, `(row+8 & 8) != 0` == assist, name `P_…` and not `…_W`.
  `_W` variant FUN_08847108 → FUN_08846e18, `_A` variant FUN_08847130 → FUN_08846f40.
- **Where an owner number comes from** (all callers checked): battle/menu fighter loads (playable owners);
  costume mask FUN_088d5e0c (unlock row owners; costumes 4..12 only); world-map party FUN_0891521c (leader +0x5C,
  4 members +0x6D4 — playable owners); world-map enemies FUN_089121f4/08912304 and FUN_08b43374 via the `enmp`
  table (system.bin chunk `enmp`, 1,267 rows of 0x24 B, +2 owner, +3 costume): **no enmp row has owner 34** (clean and
  oracle; owner 33 has 3 = ids 2320-2322); world-map leader FUN_08921248 (indirect callers FUN_08920a3c/08920a7c,
  WORLDMAP_CHAIN; owner source not resolved statically).
- **No story code asks for "owner 34"** as far as static reading goes: Cosmos's rows (id 1338 `P_ORG800_1P`, owner 34
  costume 1 flag 0; id 1339 `P_ORG800_1P_W`, owner 34 costume 1 flag 8) are reached by id.

### 3.2 The catch: companion files are re-resolved by owner
Every model load (async state machine FUN_08846a3c and sync loader FUN_08845230) picks the model's `.cosx`
(FUN_08843710, string `cosx` at 0x089C8898) and `.exex` (FUN_08843854, `exex` at 0x089C88A0; only for `P_` rows
without the assist bit and not `_W`) from **`FUN_088470dc(row.owner, row.costume, 0)`**, not from the loaded row
(unless the name starts `Z_`; owner 0 = no cosx). File name = `obj/%s.%s` (FUN_08844fa4) of the resolved row.
Fallbacks FUN_08844fe4 (gmo/objx load failure only) use `(row.owner, costume 1)`.

So for Cosmos loaded by id 1338/1339:
| test-fighter rows | battle lookup (34, c) | Cosmos's companion in story | verdict |
|---|---|---|---|
| none (today) | — | `P_ORG800_1P.cosx` | PASS |
| ids < 1338 (the P0.4 rule, needed so the fighter is found) | test fighter ✓ | **`obj/P_TST034_1P.cosx` + `.exex` (Cloud's) for Cosmos** | **FAIL** |
| ids > 1338 | **Cosmos's `P_ORG800_1P` (no objx → no fighter)** | `P_ORG800_1P.cosx` | **FAIL** |
| ids < 1338 + **fix F6**: Cosmos rows 1338/1339 costume byte (+7) 1 → 15 | test fighter ✓ | `P_ORG800_1P.cosx` ✓ | **PASS (static)** |

### 3.3 Fix options
- **F6 (recommended, data, 2 bytes, generic):** objentry rows 1338 and 1339: costume byte +7 `01` → `0F`. Ids and
  owner stay (story id lookups unchanged); the companion lookup `(34, 15)` finds only Cosmos's rows; the costume mask
  loop (4..12) and battle costumes (1..6) never ask for 15. It is an engine-base data edit made once (part of the
  engine patch whenever any package takes owner 34), not fighter code. **Risk:** any vanilla `(34, 1)` request for
  Cosmos (e.g. world-map leader FUN_08921248, whose callers are indirect) would now return the test fighter (or NULL
  without a test fighter, and FUN_08921248 dereferences without a NULL check) → that is what the runtime check rules out.
- **F2 (generic code, P2.3-style hook):** in FUN_08843710 / FUN_08843854 / FUN_08845230 keep the re-resolved row only
  if its objx key (+0x34, first 8 chars) equals the loaded row's key, else use the loaded row's own base name. Fixes
  every future "event model shares an owner" case; costs ~3 hook sites + a helper (~20 words).
- F1 (owner 0 for Cosmos rows): drops Cosmos's `.cosx` entirely (owner 0 = no cosx) → changes vanilla Cosmos. No.
- Moving the fighter to owner 35: fails grid bounds, chrp, Opponent Info rows (end at 34), stats block. No.

## 5. Package-format gap found (blocks two packages in one install)
**Update 2026-10-22:** closed by package format 1.1 (P2.8 step E2: identity-keyed codecs; tables without a codec yet
are `bytes.v1`, one editor only). See [docs/PACKAGE-FORMAT.md](../../docs/PACKAGE-FORMAT.md) and [P2.8-build.md](P2.8-build.md) §2.

Sora's rows for several shared tables are **byte-offset edits of the clean node**, including count/offset bytes:
`acab.json` = 34 `replace` rows (e.g. at 8: `21` → `22`), `amas` 33, `chrl` 33, `brai_seco` 11 replace + 4 add,
texts/blurbs/OQ names with `delete`+`replace`. PACKAGE-FORMAT §7: "two packages must not touch the same (table, ns,
key)" and §15: "row-count fields are derived" **only for grid leaves**; bytes leaves store counts/offsets as rows.
A second package appending to acab/amas/chrl/brai/texts must change the same count bytes → validator error
"same row touched twice", or a wrong table if forced. **Fix before P2.9 (P2.8 owner):** codecs that turn these
bytes leaves into owner-keyed rows (`key: {owner}` + derived header), as done for the grid leaves, then re-extract
Sora (UNMATCHED 0, pkgapply REPRODUCES) and author testfighter against the codec. Same for menu-pack picture appends
(`menu_scene_packs.json` 1,192 `add` rows keyed by final index: a second package's indices depend on install order →
key by (owner, scene, slot) and let the installer assign indices = the registry's pic_slot).
