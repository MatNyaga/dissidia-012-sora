## In plain words (for Mat)
- **Saves.** The game's save file stores progress for 31 fighters. Sora's progress lives in the space of **friend card
  25**. That is why the friend-card list holds 24 instead of 25. A second fighter (owner 34) gets the space of
  **friend card 24**, so the list drops to 23. The rule is simple: **each extra fighter costs one friend-card slot**,
  which you already approved. The save file keeps its exact size and layout.
- **When a pack is added to a save that is already full**, the game drops the **oldest unlocked** card. It does the
  same thing when a new card arrives on a full list. Locked cards are never dropped. Sora's own progress never changes.
  Old Sora saves load exactly as they do today when Sora is the only pack.
- **If you remove a pack later**, its progress stays in the save until a new friend card lands in that slot. Then it
  is gone. If you add the pack back before that, its progress comes back.
- **Owner 34 is the last fighter the save format can hold** without new save work. The Records numbers have room for
  owners 0..34 only. Owner 35 would overwrite the "total" row.
- **Room in the game's tables.** A second fighter fits today in about half of the tables. Some need a small move or a
  few code words. Three things are full and need real work: the **Records screen list** (32 entries), the
  **"who can equip this" Characters panel** (31 cells), and the **equipment-preset buffer**. For the throw-away test
  fighter these can just be left out (a "known limit"). A real second fighter needs them fixed.

### A.1 How Sora's record works today (oracle R4, bytes + decompile)
- **Save base** = the u32 at 0x089D712C (RAM; Mat's 100 % save copy: 0x08BAED38). The save blob is 0x3ECC8 B at base+0xF08. New game memsets it
  (FUN_088ab800). There is no per-section checksum in game code; the PSP savedata layer hashes the whole file.
- **Vanilla records:** 31 × 0x778 B at base+0xF58, one per owner of the list 0x089CBC98 = [1..22, 24..32] (bytes
  confirmed on oracle + clean). Chaos 23, Aerith/Sora 33 and Cosmos 34 have none. Vanilla GET_RECORD (FUN_088cb164) gave them the shared,
  unsaved global 0x09AEFAFC.
- **Friend cards:** list = base+0x1FECC, 25 × 0x10A8 B, count u32 = list+0x1A068 = **base+0x39F34**. Card functions
  (clean decompile): init loop FUN_088f520c (cap 25 = 0x19 at 0x088F523C: memsets the ghost data of cards 0..cap−1),
  add FUN_088f526c (dedupe FUN_088f56ec; `count < cap` appends at index count (cap 25 at 0x088F52A0); else
  copies over the **oldest unlocked** (+0x1C time, +0x27 bit 0) among the `count` cards), delete FUN_088f53f4 (shift
  down to count−1). FUN_088f5508 = locked-card limit (more than 8 locked = refuse). Every write is below `count` or `cap`.
- **Sora's record = card 25's bytes:** base+0x38F98 = list + 24·0x10A8 + 0x10C (card +0x10C..+0x884, inside its ghost
  data; card 24 ends at base+0x39F34 = the count word, not touched).
- **Oracle code** (bytes dumped): GET_RECORD 0x088CB164 (34 words, spot33_save + spot33_savefix): LOOKUP (FUN_088cb3b4
  rewritten as a loop over 0x089CBC98) → index ≥ 0 → base + 0xF58 + idx·0x778; else owner 33 → the record address
  base+0x38F98 → **SORA_REC** cave 0x088CB2C0 (54 of 61 words of dead FUN_088cb2c0); else the blank
  record. Friend-card caps at 0x088F523C and 0x088F52A0: 24 (clean 25 = 0x19).
- **SORA_REC (the migration that frees card 25):** (1) count ≥ 25 → count = 24. If the slot already holds a valid
  Sora record (owner byte 33, level 1..100), the old card is simply dropped from the count: case 1a, saves used with test20..test343.
  Otherwise the game's own receive-card FUN_088f526c(list, card 24) puts card 25 over the oldest unlocked card,
  then the record is set up fresh. (2) rec[0] ≠ 33 → FUN_088cbbb4(rec, 33) = reset + owner + Lv1 + preset 250.
  (3) Catch-up: rec+0x777 ≠ 0xC1 → FUN_088cbd24(rec, 1, level), mark 0xC1. Runtime PASS on a copy of the 100 % save
  (notes/release-save-safety.md §7). The "fresh 25-card" branch (1b) was never run at runtime.

### A.2 Design for owner 34 (and the generic rule)
1. **Slot rule: `record_slot = 57 − owner`.** Sora gets slot 24 (0-based: the 25th card) and owner 34 gets slot 23 (the 24th card), the plan's numbers. The slot follows from the
   owner number, and owners are already unique and fixed per package. So a slot **never moves** when packs are added,
   removed or reordered. If the slot were "the n-th package in the list", removing a pack would shift the others onto
   someone else's record. That would wipe two fighters' progress.
2. **Friend-card limit `cap = min(record_slot of installed packages)` = 57 − highest installed owner** (Sora only: 24;
   Sora + 34: 23; 34 only: 23, card 24 stays unused). The installer writes both cap words (0x088F523C init loop,
   0x088F52A0 add) as data (P2.1 mechanism I). Both must change together: the init loop would otherwise memset slot 23's record.
   With owners ≤ 34 this equals the plan's "25 − package count". Use the min-slot form so a removed middle pack can never
   hand its slot to cards while another pack still uses a lower slot.
3. **GET_RECORD, generic:** list owner → vanilla record (unchanged); else registry row with RECORD_SLOT → `rec = base
   + 0x1FECC + slot·0x10A8 + 0x10C` (owner 34: **base+0x37EF0**); else the blank record (vanilla; also the fallback
   when EXTRA.PRX is missing). This lookup runs on every record read, and menus read a level per grid cell, so it must stay
   O(1) (REG_ROW).
4. **One migration for ALL package slots at once** (replaces SORA_REC step 1). Condition checked on every package
   record read (one load + compare): `count > cap`. Then:
   ```
   old = count; count = cap                       # cut the list first
   for i in cap .. old-1:                          # every card sitting in a package slot (or a hole)
       if valid_record(slot i, owner 57-i): keep   # 1a: already a record (old mod save) -> just not a card any more
       else: FUN_088f526c(list, list + i*0x10A8)   # re-receive: overwrites the oldest unlocked of cards 0..cap-1
   # records are set up later, lazily, per owner (step 5)
   ```
   All re-receives must happen **before** any record is set up: the card bytes are read from the slot itself. Doing it
   per owner (lazily) is wrong. Accessing owner 34 first would cut the count to 23 and silently lose card 24 before
   Sora's turn. With N = 1 this is exactly today's SORA_REC.
5. **Per owner (unchanged logic):** `rec[0] ≠ owner` → FUN_088cbbb4(rec, owner); then the catch-up with a per-package
   MARK (registry params; Sora keeps 0xC1).
6. **valid_record(slot, o)** = `rec[0] == o && 1 ≤ rec[1] ≤ 100`, and for owners other than 33 also `rec[0x777] ≠ 0`
   (the marker is set on first use). Sora keeps the old 2-byte test because 1.0-era saves carry marker 00 in the
   damaged-25-card state. What a real card holds at +0x10C/+0x10D/+0x883 (ghost data) is **unconfirmed**. A false
   "valid" would drop one card without re-receiving it, so the marker makes this less likely for new owners.
7. **Code budget:** today 34 (GET_RECORD) + 54/61 (cave) words. The generic version (lookup + loop + init + catch-up,
   ≈ 80-100 words) does not fit the cave. Use the P2.1 helper range (after P2.4 frees EXRUN/EXITEMS) or a behaviour
   stub into EXTRA.PRX (resident; missing module → blank record = vanilla behaviour, safe). Inventory v2 #3 and P2.0 risk 1 say the
   same about room.
8. **OQ "has record"** (0x089293DC, spot33_oqrecord: `owner == 33 → 1`) → "is a package owner with RECORD_SLOT". Its
   bound (< 35) already admits 34.

### A.3 Behaviour when packs change (with the slot rule above)
| situation | what happens | player loses |
|---|---|---|
| old 1.0 Sora save, engine disc with Sora only | cap 24, slot 24: same code path and bytes as 1.0 | nothing |
| save with ≤ 23 cards, add pack 34 | slot 23 is outside the list; record set up at first use | nothing |
| save with 24 cards (1.0 maximum), add pack 34 | count 24 > cap 23 → card at index 23 re-received → the **oldest unlocked** card is replaced | 1 card (the oldest unlocked) |
| vanilla 25-card save, Sora + 34 | cards 23 and 24 re-received → the 2 oldest unlocked cards go | 2 cards |
| remove pack 34 (Sora stays) | cap back to 24; slot 23 is a normal card slot again; record stays until the 24th card arrives there | test fighter's progress once a card lands there (pack is gone anyway) |
| re-add pack 34 later | slot 23 still a valid record → kept; was overwritten by a card → that card is re-received, fresh Lv1 | progress only if a card overwrote it |
| remove Sora, keep 34 | cap stays 23 (min slot); Sora's record stays untouched beyond the list | nothing (one slot unused) |
| vanilla round trip (mod save on the clean game) | vanilla fills slots 23/24 with cards → back on the mod: re-received, records reset to Lv1 | as 1.0's downgrade policy: not supported, back up |
| more than 8 locked cards | not possible (FUN_088f5508 refuses a 9th). Re-receive never replaces a locked card | – |
- **Never affected:** save size/layout, the 31 vanilla records, the stats blocks (owners ≤ 34), flags.
- **Known gap (unconfirmed, low):** the Friend Card menu (OVL_MENU_APP FUN_08a1cd14 / FUN_08a1e6b4 / FUN_08a1f730,
  object +0x2BBC) keeps its own 25-entry display arrays and uses 0x19 as "no card". Every index there comes from the
  save count, and no write past `count` was found. A full-list runtime test still has to show nothing odd at 23/24 cards.
- The player's own card can carry a favourite/ghost owner. Sending owner 34 to an unmodded player is out of scope
  (same policy as Sora: FUN_088cb1ec "has record" stays false for package owners at the ghost/card sites).
