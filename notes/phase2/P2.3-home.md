# P2.3 step 3 — the home decision (OXT vs REG_ROW, key-string home, menu gap)

Written 2026-10-21 by Claude (P2.3 lookups helper). Gate for steps 4-7 ([P2.3-lookups.md](P2.3-lookups.md) §4 step 3,
§5 Q1/Q2/Q8). Built on it: [P2.3-pictures.md](P2.3-pictures.md), [P2.3-museum.md](P2.3-museum.md),
[P2.3-oqface.md](P2.3-oqface.md), [P2.3-flags.md](P2.3-flags.md). ABI: [docs/ENGINE.md](../../docs/ENGINE.md) block
"P2.3 steps 3-7 — as built".

## In plain words (for Mat)
- Many menus ask "which picture / frame / record icon belongs to fighter N?". The answer now comes from **small
  per-fighter tables** that the installer writes into a piece of the game's own code memory that P2.4 freed (an old
  function the game never calls). They cost the same as the original game: one memory read, no extra code to run,
  so the Vita menus are not slowed down. They also keep working if our module fails to load.
- Only two places use the module's registry at run time: the **Labyrinth music fallback** (it asks "does this fighter
  have a registry row?") and the **Jukebox gates** (they ask "is this a fighter-pack purchase flag?"). Both run only
  when a list is built or a battle starts, never every frame.
- A second fighter's 6-letter file key (owner 34) gets a 16-byte "key string pool" in the same memory block.
- The big empty area after the menu overlay ("menu gap") is **not needed**: everything fits into the freed block, and
  using the gap would mean making a game file longer (a risk on the Vita) for no gain.

## 1. Q1 — OXT (installer-written per-owner tables) vs REG_ROW: **OXT for every table-shaped lookup**
Confirms PHASE2-START decision 1 now that the space exists. Numbers:
| | OXT (as built) | REG_ROW (the alternative) |
|---|---|---|
| per-call cost | 4 instructions incl. 1 load (`sll / lui / addu / lh`) = R4's 4-word remap; vanilla had 2 words plus 2 redundant ones | `jal` + REG_ROW's 9-12 instructions + field load + a trampoline at most menu sites (no room for 5-6 words in place) ≈ 15-20 |
| measured | every picture / frame / setup / viewer / Records / OQ screen within ±4 % of the oracle (frame median busy ticks; the sites are not called on still frames, breakpoint evidence), list/scroll worst frames within the same spread | not built |
| needs the module | no (module-missing control: pictures, viewer, OQ face, Records still right) | yes (REG_PTR) |
| static check | yes: the tables are bytes on the disc (`p23_lookups.py --dry` = "already", host test, equiv by id) | no (data in EXTRA.REG) |
| installer | writes ≈ 500 B of tables from the registry source + clean vanilla columns (`tools/pkg/engine/patches/p23_lookups.py`; rowgen-style, roster-wide) | nothing beyond EXTRA.REG |
| space | 0x1F8 B of tables + 76 helper words in the freed block (20 words spare) | ≈ 70 helper words + per-site trampolines |
Vanilla cost wins ties (Mat's Vita menus); OXT is vanilla cost and module-independent, so OXT. **REG_ROW / registry
data stay for:** the BGM mode-7 fallback (decision 4: "does the opponent have a registry row") and the Jukebox gates
(flag ranges live in EXTRA.REG; one list for all packages, list builders only).

Tables index the owner directly (no bound): an owner ≥ 36 reads past the table into the next one, like vanilla's
`base + owner − 1` reads past its run. Only owners 0..35 exist (owner limit 35).

## 3. Q8 — owner-34 key string: **EBOOT KEY_POOL (0x089A8D7C, 2 × 8 B)**
EBOOT is always mapped, so all five name-key pointer tables (EBOOT 0x089D6CA8, battle 0x08AFBC68, menu 0x089EA3C4 /
0x089EC56C / 0x08B57FBC) can point at one string there; no per-image copy, no overlay space. Sora reuses vanilla
`sev120` (pool stays zero). The installer step (rowgen D5 "(3) a 4-aligned copy of key\0" → the pool) is P2.8 work;
test34's 5 key refusals in rowgen stand until then (P2.3-rowgen §4).

## 4. Q2 — menu gap 0x08B59258-0x08B63170: **skipped**
The freed EBOOT block holds every P2.3 table and helper with 20 words to spare, and 364 more free words remain
(jump table + post-fallback area). Using the gap would need (a) a runtime write-watch proof, (b) a longer
OVL_MENU_APP.ELF (the loader must read more; Vita risk; the battle cave precedent was removed in P2.4 for exactly that
reason — "no package code inside a game file") and (c) menu-only code could not serve EBOOT callers (BGM). Menu code
reaching EBOOT tables costs nothing extra (EBOOT is always mapped). Q2 stays open only as a possible P2.7 buffer home.
