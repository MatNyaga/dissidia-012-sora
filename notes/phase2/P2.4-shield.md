## In plain words (for Mat)
- **Save the King** (Sora's accessory: a hit his EX Reflect sends back is 1.5× as strong) was the last piece of
  hand-written item code in the game's main program. It is C code in our module now.
- Its little helper block ("EE_B": "does Sora wear item X?", "which player slot is he?", "give EX gauge") had no other
  user left after step 2. That block and Save the King's own code are back to the **original game bytes** now. Those
  bytes belong to a function the game never calls, so that space is free again for the next steps.
- The number 1.5 now lives in one place only: the item table of Sora's package (`item_fx`, "REFLECT_POWER 1.5"). The old
  second copy (`params.shield_pct` = 192) is gone, and the registry tool refuses it if someone adds it again.
- An offline test runs the **old** Save the King code in a tiny emulator next to the **new** C code on the same fake hits:
  every result is identical, including odd powers and negative numbers. Five deliberately broken versions of the C were
  all caught.
- On the emulator, side by side with the reference disc and the same scripted steps: every hit Sora's EX Reflect sends
  back at Lightning has **power 150 with Save the King and 100 without, on both discs** (30 + 35 reflected hits with the
  item, 15 + 14 without). Reflect, the HP-attack reflect, Lightning's spells bouncing back, the Crown Pendant (EX lasts
  ×1.3), Trinity Limit and Cloud's guard all behave as before. Without the module (or without the registry) nothing
  hangs; Sora's guard is then a normal guard.

## 2. Port details (R4's SHIELD vs the C)
R4 (spot33_exitems.py SHIELD, EBOOT 0x089A8D24, 23 words), called at the end of FUN_08807860 (the hit builder: its call to
FUN_089A3890 → a call to SHIELD), in pseudo-code:
```
t3 = hit+0x18 (source), t4 = hit+0x20 (owner); if t4 == t3 || t4 == 0 || t3 == 0 -> tail
if EE_HAS(t3, 680): power(hit+0x2a) = (signed 16-bit power × 192) >> 7   (arithmetic shift, 16-bit store)
tail: on to 0x089A3890 (a0 = hit)
```
- **Integer math checked in mips_emu before choosing the C:** signed 16-bit load, signed 32×32 multiply, low word,
  arithmetic shift right 7, 16-bit store. C: `int p = (int)(short)U16(hit,0x2A) * q7; U16(hit,0x2A) = (unsigned
  short)(p >> 7);` — psp-gcc emits exactly `lh / mult / mflo / sra 7 / sh` (disassembly checked). q7 = round(1.5 × 128)
  = 192 is computed once at load from the item_fx float. (Logical vs arithmetic shift cannot differ in the stored 16 bits;
  the sign of the LOAD matters, and a planted "unsigned power" bug is caught.) Results: 100 → 150, 37 → 55, −37 → −56,
  1 → 1, −1 → −2, 85 → 127, 0x7FFF → 0xBFFE, −0x8000 → 0x4000 (16-bit wrap kept).
- **Call site:** FUN_089A3890 = "zero 16 bytes at a0, return a0" (reads a0 only). After the site (0x088079B4..) the
  caller uses only s-registers and a fresh a0, so nothing caller-saved is live; R4 itself left a1 = 680 and t3-t7
  changed. `wrap_shield` = CALLSITE_WRAP (saves a0-a3, t0-t3, f12-f19, ra; frame 0x50), `beh_shield(a0)`, then
  vanilla[20] with every argument register restored. beh_shield calls no game function (no thunk needed).
- **Deliberate difference:** R4 asked EE_HAS(source, 680) for ANY source; the module asks the registry first (the
  source's owner must have an ITEM_EFFECTS row owning a REFLECT_POWER item, then that item must be in the live loadout).
  Only Sora can equip 680, so this differs only in an impossible state (C-only host case "Save the King on Cloud":
  R4 ×1.5, module ×1.0).
- Who builds reflected hits: C2 → FUN_08808468(B, id | 0x4000, A, dir, 1) → C4 fallback (mark 0x4000: owner a1 =
  attacker) → FUN_08807860 with source = Sora, owner = the attacker → SHIELD at its end.

## 3. EE_B freed — users, and what "free" means
- `p24_refscan.py` on **P24-reflect**: SHIELD 0x089A8D24-0x089A8D80 has one outside user (EBOOT 0x088079AC = the S20
  hook); EE_B 0x089A8DE4-0x089A8F0C has one outside user (0x089A8D4C = SHIELD's `jal EE_HAS`). Controls: the oracle shows
  8 EE_B users (EE_A ×7 in the TRI range + the cave's HELM), tri2 shows 2 (SHIELD + cave HELM). On **P24-shield**: 0
  outside users of either range (only the dead function's own internal branches in the clean words).
- **The clean words are not empty space:** 0x089A8B14-0x089A8F0C is a vanilla function (a format-driven unpacker with
  callbacks) that the game never calls: no j/jal/branch/pointer/lui pair anywhere in the clean EBOOT or the three
  overlays points into it from outside, except its own switch table 0x089D1FB4 (dead with it) — re-checked with
  p24_refscan on the clean images (0 hits) and proven at runtime by the test272p probe (notes/ex-burst-controller.md
  §21). "Free" = unreachable vanilla code: putting the clean bytes back makes those words exactly vanilla again (equiv
  shows them as "differs from the oracle", the oracle being R4), and a later step may overwrite them like before.
- The 13 words 0x089A8EA8-0x089A8EDB were clean on R4 already; 61 + 23 = 84 words changed.

## 4. Decision: `params.shield_pct` vs item_fx REFLECT_POWER → keep **item_fx REFLECT_POWER**
- It is the registry's design: the item table says what each item does (EX_HIT_GAIN 678, EX_GUARD_GAIN 679,
  REFLECT_POWER 680, EX_DRAIN 681) for items the row's owner owns; EE_HIT, EE_GUARD and HELM already read it. A fighter
  with two shield items, or another fighter's own shield item, needs no new row field.
- It ties the number to the item that causes it (no item → no effect, ownership checked by the same item_owner table),
  while params.shield_pct was a per-fighter number nobody read and that could disagree with item_fx (192/128 vs 1.5).
- The u16 slot stays (written 0) so the behaviours-v1 byte offsets (voice_bar 0x38, crown_drain 0x3C) do not move.
- Same pattern left over (not changed here, open question Q-S1): `params.crown_drain` duplicates item_fx EX_DRAIN and is
  not read by the module either.

## 7. Problems / lessons
- **The first player pick landed on Squall** (boot_nav press timing on a loaded machine) — caught on the setup
  screenshot before any battle; fixed by hand (Circle back, select Sora). Always look at the setup screenshot.
- **Menus can swallow presses** when the PC is busy: setup_enter.sh's fixed waits left the game on Opponent Info twice.
  New `ensure_battle.py` presses Cross every 12 s until player 1 is in battle (use it after every enter).
- **Reading heap objects without code breakpoints:** a memory write breakpoint on a fixed global that the code writes
  right after the interesting moment (here the hit-list tail) gives the object in a register at the pause. The pause
  lands a little later than the store (the owner word +0x20 read 0 / the player there, not the attacker), so classify
  with data that does not change afterwards (source, row id, power).
- The attacker's Bravery loss after a reflected hit is not a clean measure of power (his Bravery is capped / broken /
  refilled by the assisted steps); the hit power at the builder is.
