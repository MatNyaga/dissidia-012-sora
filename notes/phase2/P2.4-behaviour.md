## In plain words (for Mat)

- Sora's special code today is about **950 hand-written assembler instructions** in three "dead" corners of the
  game's code and in a 512-byte add-on stuck to the end of the battle code file. 28 places in the game jump into it.
- P2.4 moves that code into our own module (EXTRA.PRX) and writes it in C, reading Sora's numbers (run speed ×1.40,
  item ids, voice line, Crown Pendant ×1.30 …) from the registry instead of having them baked in. The 28 jump places
  stay where they are, but now jump to a small fixed "switchboard" (stub) that forwards to the module.
- **The module can be built today** with the same toolchain as EXTRA.PRX. I built a throw-away test module in my
  scratchpad: the compiler's calling rules match the game's, calls to game functions come out right, and the size
  is small (≈ 0.65 KB for EX run + Reflect decision + three helpers).
- After the port, the battle code file goes back to **exactly its original size**, and ~3.4 KB of EBOOT space is free
  for the switchboard and the registry helpers.
- One ordering problem: the switchboard was planned in the space Trinity Limit uses today, so Trinity (or a small
  pilot) has to move first. I give a concrete **pilot with EX run** below that works around it.
- Nothing here is expensive per frame. The menu slowness on the Vita was the CPU clock (fixed in test354), not hooks.

## 3. Every behaviour: hook sites, contract, cost, C port

Notation: E = EBOOT, B = OVL_BATTLE_APP, M = OVL_MENU_APP. "clean → R3" = the two words at the site. **Call site** =
the hook replaces a `jal` (or is a function entry/vtable call): caller-saved registers (at, v0-v1, a0-a3 except
arguments, t0-t9, f0-f19) are free. **Mid-code** = the hook replaces ordinary instructions: the listed live
registers must survive. Stubs: ENGINE.md §2 numbering (S0-S22).

Game ABI = PSP EABI (args a0-a3 **then t0-t3**: e.g. the game's calls to FUN_08808468 and FUN_088a9de8 pass a 5th
argument in t0;
callee-saved s0-s8, f20-f31). psp-gcc 15.2 in the container uses the same (`__mips_eabi`, single float; test build:
a 5-argument call puts the 5th in t0; f20-f22 saved in the prologue) → C functions can call game functions directly
and be called from wrappers with no glue.

### 3.1 EXRUN — EX Mode run speed (feature 1 EX_RUN) — **pilot (§6)**

| site | clean → R3 | target | type |
|---|---|---|---|

- Body: E 0x089A8B24, 25 words. Owner test: owner byte at *(s0+0x2f8)+6 == 33 (0x089A8B34), motion u16 s0+0x180 == 2

  vanilla path ≈ 8 instructions. Ported: stub 4 + wrapper ≈ 10 + C fast path (`row_of`: 2 loads, 1 compare) ≈ 12

## 5. Wrapper rules (what the C port must keep)

1. **Stub** (EBOOT, fixed): `lui at,%hi(FN_PTR_n) / lw at,%lo(FN_PTR_n)(at) / jr at / nop` — clobbers $at only, ra
   untouched (ENGINE.md §2). The C7 and vtable entries are entered by `jr`/`jalr`, which is fine.
2. **Call-site wrapper** (asm, in the module), for S0-S6, S9-S11, S14, S15, S17, S20, S22: save ra (+ the arguments
   the original callee still needs, incl. **t0** for C4/SCALE), move the caller's callee-saved registers the C function
   needs (s0/s1/s3/s7/fp, or the caller frame pointer) into a0-a3, `jal c_fn`, restore, then either `jr ra` with the
   result or tail-jump to `vanilla[n]` (= the FN_PTR value the module found on disc). ≈ 8-14 words each.
3. **Mid-code wrapper** for S8 (C1), S12 (C7), S13/S21 (function entries), S16, S18/S19, S24, S6 (HELM): save the live
   caller-saved registers listed in §3 — simplest safe rule: save a0-a3, t0-t9, v0, v1 (+ f12/f13 for HELM) ≈ 20 words
   each way, ≈ 45 cycles. Read anything from the caller's stack frame **before** the wrapper's own `addiu sp`.
4. **Fast path first.** For the per-frame stubs (S7 EXRUN, S6 HELM, S1 bar, S10 C3, menu S16/S18/S24) the wrapper (or
   the C function's first lines) does the "is this owner in the registry with this feature?" test before anything
   else (owner byte → `owner − 33 < REG_COUNT` → `feat` bit). P2.0's rule "behaviour stubs test package owner before
   jumping to the module" is met by doing it in the module wrapper; doing it in the EBOOT stub would need per-site
   register knowledge in a generic stub (not worth it at ≈ 10 instructions).
5. **Overlay guard:** module code that calls battle-overlay functions from an EBOOT hook (C1, C2, EE_GUARD) checks
   that the battle overlay is resident (§3.3). Menu-overlay sites (S17, S24) call menu functions only.
6. **No module addresses on disc.** Overlay words are re-read from disc on every scene change, so they may only hold
   stub addresses (fixed EBOOT). The module never patches code (data pointers only, ENGINE.md §2); the only code word
   it writes stays the P1.4 xidx hook.
7. C rules for the module (no libc, `-nostdlib`): no struct copies large enough to make gcc call memcpy, no 64-bit
   division (libgcc is not linked), floats are fine (hardware single precision: mul.s/div.s/cvt).
8. Counters: give status layout v2 a `stub_calls[32]` array (0x80 B, append-only) instead of the single
   `behaviour_calls` word: each wrapper does `lw/addiu/sw` (3 instructions) → find_status.py shows, per behaviour,
   whether and how often it ran. This is the main runtime proof tool for every P2.4 disc.

## 6. Pilot plan: EXRUN (answer to the coordinator, 2026-10-20)

*Built + tested 2026-10-20: notes/phase2/P2.4-exrun-pilot.md. Corrections from it: the hook runs once per 30 Hz
logic frame per moving fighter (not ≈ 60/s); registry ex_run_mult = 1.4 (not 1.3984375); the 6-word header has no
REG pointer, so "REG block = header + 0x18" is the rule for every XSTB version (ENGINE.md "P2.4 steps 0 + 1").*

**Why EXRUN:** 1 hook word, call-site contract, no overlay call outside battle, 25 words, measurable with an
existing tool (ppexspeed.py), and it runs **every frame for every fighter** — so it proves the stub cost on the
hottest kind of path.

**The ordering problem it must solve:** ENGINE.md fixes the stub table at 0x089C1C9C, which TRI occupies until TRI
is ported (TRI is the biggest port, a bad first step). Free EBOOT room today is ≈ 3 words per range. Proposal:
**make only a 6-word header fixed, at 0x089A8B24** (the first word EXRUN frees), and let it point to where the
arrays are:

## 7. Toolchain: can today's engine build add these modules? — yes

- Build: `tools/dlc/pspenv.sh make -C tools/pkg/engine/extra` (pspdev v20261001, container `dissidia-pspdev:1`,
  psp-gcc 15.2.0, `_MIPS_ARCH_ALLEGREX`, `__mips_eabi`, `__mips_single_float`) then
  `python3 -I tools/pkg/engine/make_manifest.py` and `python3 -I tools/pkg/engine/test/run_host_test.py`. New C files
  go into `OBJS` (e.g. `beh_exrun.o beh_tri.o beh_reflect.o beh_items.o wrap.o`); flags stay `-Os -G0 -fno-pic
  -fno-builtin`, `-nostartfiles -nostdlib`, `-lpspuser -lpspmodinfo`.
- Throw-away proof (helper scratchpad `p24/mod/`: beh.c, wrap.S, Makefile; run with the same image and an extra
  scratchpad mount, because pspenv.sh mounts only the project): EXRUN + C3 decision + 5-arg reflect queue + Crown factor
  + TRI_VT5C + 2 asm wrappers + a stub writer → `.text` 652 B, `.bss` 136 B, PRX 2,602 B (sha 298f4967…bda1).
  Checked in the disassembly: game calls come out as `lui/ori + jr/jalr` with **no relocation** (absolute addresses
  are constants); the 5th argument goes in t0; module-internal calls/pointers are R_MIPS_26 / HI16 / LO16 relocations
  that psp-prxgen turns into PRX relocations (the loader applies them, as for EXTRA.PRX v1). psp-prxgen needs at least
  one import (a module with no import fails "no .lib.stub section").
- How a stub reaches module code: the stub is in EBOOT (never moves, same 256 MB segment as every overlay, so a plain
  `jal STUB` works from any image); it loads FN_PTR (a data word the module wrote in module_start) and `jr`s to the
  module's wrapper. Overlays are re-read from disc on each scene change; that is harmless because they hold only
  stub addresses. PPSSPP's JIT: the stub's `lw` is a real load each call, so a block compiled before module_start
  still follows the new pointer (P2.1 claim; the pilot's step 1 proves it).
- Size / memory: v1 module 3,680 B in RAM. Estimate for all of P2.4: asm 3.7 KB × ≈ 1.5 + 25 wrappers × ≈ 12 words
  (1.2 KB) + registry loader/stub writer ≈ 1.5 KB → **≈ 9-10 KB more** (module ≈ 13-14 KB + 12 B per EXTRA.IDX row),
  inside ENGINE.md's 16-20 KB estimate. P0.3: 4.1 MB free at module start, 445,440 B total / 247,040 B largest block
  after the game's heaps — the module is loaded before those heaps, so it comes out of that slack (≈ 3 %).
- Host tests can check the C logic against the asm's known answers offline: SCALE for every level 1-100 × 4 items vs
  `spot33_exitems.scale_value`; TRI_HPROW on the 136 atkp tables of the disc (the offline walk from test317); ENSURE /
  NEWGAME on synthetic inventories (old save, new save, full list); EXRUN gates.
