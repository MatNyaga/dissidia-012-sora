## In plain words (for Mat)
- "Lookups" are the spots where a menu asks "which picture, name or frame belongs to fighter N?". Today about 25 of
  them have an answer written in just for Sora (owner 33).
- **14 of them are plain table rows.** The package already stores them as data. The engine needs nothing new there,
  only an installer step that writes the row for each fighter from its registry values. A second fighter (owner 34)
  has a free row in 8 of these tables. The other 6 tables are full, so they belong to P2.7 (capacity).
- **11 are small pieces of code.** Two of them (the name lookups) can be made generic right away, in the space they
  already use. Most of the rest need a little free memory that Sora's own code still holds today.
- Good news: all the game's "fighter → name" tables hold the same numbers, so one table row per fighter drives
  every name on every screen.
- My main suggestion: for the picture, frame and museum lookups, write small per-fighter tables at install time
  instead of looking things up in the module's registry while the game runs. The code stays the same size and
  speed as the original game. The installer can check the rows offline, and they keep working even if the module
  fails to load.

## 1. Mechanisms used below
- **I-row** (install-time data row): the installer writes `table[index(owner)] = value` from the registry source.
  Already how the package applies these (img: rows). Zero runtime cost. A static check can see it
  (tools/qa/owner_rows-style, PACKAGE-ACCEPTANCE A7).
- **I-imm** (install-time immediate): an immediate constant in code whose value depends on the roster (caps, bounds).
  The installer writes it. Zero cost.
- **OXT** (proposal, *owner-extension table*): a small fixed table indexed by owner (0..63), written by the installer,
  holding vanilla values for owners 0..32 and package values for 33..63. Code changes only the base/bound of its
  load, and in most sites the change has the **same size** as today's owner-33 block. Runtime cost = one vanilla load.
  Home: menu-only tables → menu gap (§0.5) or EBOOT freed range. Name tables don't need one (§0.3).
- **L** (ENGINE v2 registry lookup): `jal REG_ROW` (a0 = owner → v0 = &row, clobbers at, v0) + `lhu FIELD(v0)`,
  ≈ 4–6 words per site + helpers ≈ 63–70 words. Needs EXTRA.PRX loaded (REG_PTR ≠ 0), otherwise the vanilla path runs.
  Kept as the documented alternative to OXT for every code site.
- **S** (behaviour stub): not used by P2.3 (lookups do not need module code).

**OXT vs L (my recommendation: OXT for every table-shaped lookup, L only where a loop over packages is unavoidable):**
| | OXT | L (ENGINE v2) |
|---|---|---|
| code per site | 4 words, mostly in place (picture REMAP 4 → 4) | 4–6 words + `jal` → most menu sites need a trampoline (the coordinator noted these sites were rewritten to the same length) |
| per-frame cost | = vanilla (1 indexed load) | ≈ 15 instructions + call; ra clobber (OK only in non-leaf functions) |
| needs module | no (works on layout A/R/B/C) | yes (REG_PTR) |
| static check | yes (bytes on disc) | no (data lives in EXTRA.REG) |
| space | ≈ 640–770 B of tables (+ ≈ 15 words for REG_FLAG) | ≈ 70 words of helpers + trampolines |
| Phase 4 (drop-in DLC) | the module can fill the same tables at boot | native |

The registry SOURCE (`tools/dlc/registry/*.json`) stays the single source of truth for both. With OXT, the EXTRA.REG
row fields name_index / pic_slot / pic_slot_party / party_frame / setup_frame / oq_* are read by no runtime code
(they can stay for diagnostics). That is a P2.1 design change → review question Q1.

**Helper-space answer (coordinator's request):** names need **0** new words. With OXT, the rest needs ≈ 640–770 B of
tables + ≈ 15 words (REG_FLAG) + ≈ 10 words of OQ builder growth. All of it is menu-only, so it fits the menu gap with
no EBOOT space at all. With L, the helper block is ≈ 70 words (REG_ROW 14, REG_FIELDT 16, REG_FLAG 14, REG_NEXT 14,
REG_BY_MUSEUM 12) plus trampolines for the menu sites that grow (setup banner +1/+2, party slots, viewer). Homes in
order of preference: (1) menu gap (after the runtime watch), (2) EXITEMS/EXRUN range once P2.4 moves those
(250 words), (3) scraps (≤ 13 contiguous words, not enough), (4) FUN_08893558 (29 words, unconfirmed).

## 4. Recommended order (smallest/safest first) and grouping
Each step = its own test disc (`cp --reflink=auto` of the oracle-built base, base image confirmed through
codex/QUESTIONS.md first). Then `equiv.py ORACLE DISC --expect-engine` (only the step's sites may differ; P2.0 asks
for `--allow-site ID`), then the targeted check + control from §2.
1. **Row generator (D1–D3, D5–D8, D12, D14)**: installer/registry tool computes the img:/file rows from registry
   values + a machine-readable table spec (base, stride, index base, format, max owner). Sora's values are unchanged,
   so **equiv must be IDENTICAL**. No runtime test needed beyond a smoke. Proves the generator before any code moves.
2. **Names group (C1 + C2; data D1/D6 already rows)**: two in-place rewrites, no new space, vanilla cost. equiv: only
   0x088D6254.. and 0x08A1D7FC.. differ. R: Records, Friend Card / Ghost, Labyrinth names, Opponent Info.

4. **Pictures group (C3 + C4 + C5)**: one PIC_IDX table shared by 13 + 2 sites, PARTY_FRAME, SETUP_DELTA. One disc.
   R: the 6 scenes in C3 + setup banner + party frame, each with a control fighter, + B15 tick count (per-frame paths).
5. **Museum group (C6 + D4 REC_ICON)**: viewer owner table. R: View Character 6 outfits.
6. **OQ face (C7)** with the D7 pair moved to OQ_PAIR. R: OQ slot face after re-entering the scene.

8. Hand-offs: C8, C9, D9–D11, D13 → P2.7. C11 → P2.5. The 0x7F drop immediate (D14) gets the "only if owner 33 is

one OXT block (one relocatable data area, one installer writer).
