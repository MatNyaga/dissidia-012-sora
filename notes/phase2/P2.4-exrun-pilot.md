# P2.4 step 0 — infrastructure + EXRUN pilot (built + tested)

Written 2026-10-20 by Claude (EXRUN pilot helper). Design: [P2.4-behaviour.md](P2.4-behaviour.md) §6 (pilot) +
parent decisions (header-indirect XSTB at 0x089A8B24, REG_PTR/REG_COUNT + FN_PTR + 1 stub + 1 fallback + 12-word
REG_ROW in the 28 freed words, registry state separate from EXTRA.IDX state, publish registry first / stub pointers
last, vanilla-safe without module or registry). ABI background: [docs/ENGINE.md](../../docs/ENGINE.md) §"Registry +
stubs v2". Review input: [P2.1-review.md](P2.1-review.md).

## In plain words (for Mat)
- Sora's "run 40 % faster in EX Mode" no longer lives as hand-written code inside the game. The game now jumps to a
  tiny fixed **switchboard** (4 instructions) that asks a pointer where to go. Our module (EXTRA.PRX v2) loads Sora's
  numbers from a small data file (EXTRA.REG) at boot and points the switchboard at its own code; without the module
  or without the file the pointer keeps pointing at the original game code, so everyone runs at normal speed and
  nothing breaks.
- The pilot disc is a copy of the frozen Phase-2 oracle with only this change. A disc checker confirms that nothing
  else differs.
- On the emulator Sora runs exactly as fast as on the oracle disc (×1.40 in EX Mode), Cloud is unchanged, and with
  the module or the data file removed everyone runs at normal speed and nothing crashes. The extra cost per frame is
  far below what can be measured.
- The test found one wrong number in Sora's registry file (1.3984 instead of 1.40); fixed, pilot rebuilt.

clean rebuilds identical): .text 5,000 B, .bss 512 B; symbols (module base offsets): wrap_exrun 0x48, beh_exrun

wrap_exrun fast path for a vanilla fighter: 4 (counter) + 12 (owner test) + 4 (jump to vanilla[0]) + fallback 2 =

## 5. Problems / lessons
- **Registry value was wrong** (1.3984375 vs the built 1.4): only a runtime A/B against the oracle caught it (equiv
  cannot: the constant moved from code into EXTRA.REG). Rule for every P2.4 step: compare the behaviour's measured
  numbers pilot vs oracle, not vs the research note; and registry values for constants come from decoding the WHOLE
  built constant (lui + ori/addiu pair), never the lui alone.
- Call rate: the EXRUN hook runs once per 30 Hz battle logic frame per fighter in movement states (frame counter
  +0x324 advances 30/s at 60 vblanks/s), 0 in hit/attack states — not "60/s per fighter".
- Measuring run speed: whole-run distance/frames is wrong under the debugger (the game runs ~8-10 fps while polled,
  so the acceleration phase is not excluded) and stage pillars/edges spoil long runs; CPU hits drain EX Mode. What
  works: one debugger connection for the whole sequence, player placed on an open straight line, CPU parked 25 units
  ahead every 0.25 s, HP refilled, median per-frame speed + the +0xBC scalar (exrun_seq.py).
- PPSSPP's debugger server refuses quick reconnects for up to ~15 s now and then (Recv-Q 1 on the listener, a
  CLOSE-WAIT socket): keep one connection per sequence; p24rt.connect retries 20 × 0.7 s.
- Another helper started a second PPSSPP while this one ran (P2.3 names, port 41337): screenshots by window title
  grabbed the wrong window once (deleted). shot.sh now refuses to guess when 2+ game windows exist (`WIN=0x…`).
- A blind boot sequence drifted into Extras → Data Install on a fresh profile (cancelled, profile only): nav_setup.sh
  now starts at the main menu; boot + Load by hand with screenshots.
- install.py (P1.3 package installer, release 1.0 / p18) reads tools/pkg/engine/extra/extra.prx and checks it
  against engine.json → the v2 module must not replace extra.prx. Kept v1 bytes identical and built v2 as a second
  target (extra_v2.prx / engine_v2.json / `install_engine.py --engine v2`).
- The 6-word header has no REG-block pointer; the module needs to find REG_PTR/REG_COUNT. Rule used: **XSTB version 1
  ⇒ REG block at header + 0x18/+0x1C**. When the arrays move to the TRI range, bump the version (and add the P2.1
  review's abi_hash) instead of reinterpreting version 1.
- The module does NOT call the EBOOT REG_ROW (its address is not in the header; the module trusts only the header).
  wrap_exrun uses the module's own owner mask. REG_ROW is checked live by emulating its 12 words against the live
  REG block (tools/qa/runtime/p24_regrow_check.py, §4).
