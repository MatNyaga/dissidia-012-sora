## In plain words (for Mat)
- Sora's four items (Kingdom Key, Protect Belt, Save the King, Crown Pendant) used to need ten small pieces of
  hand-written game code with "is it owner 33?" and "is it item 678-681?" baked in: who may equip them, the Customization
  and Shop lists, the "Can be equipped by" □ panel, giving them on a new game or to an old save, the stats that grow
  with Sora's level, and Sora's own face and name on the EX Mode page. All ten now run as C code in our module and
  read their numbers from Sora's package table (the registry). Nothing in the game's own code says "Sora" any more for
  items.
- The old code is gone. Its space (about 220 instructions) is back to the original game bytes, as is the little
  table it borrowed for the level scaling.
- The registry learned three things: which items a fighter owns **from the start**, the level-scaling table, and
  which EX-page pictures to show. The old unused copy of the Crown Pendant number was removed (the item table has it).
- Side by side with the reference disc, with the same button presses: Sora's lists, the panel (Kingdom Key lights only
  Sora), the EX Mode page, the Lv42 stats (ATK +45, HP +2086, DEF +47, BRV +191), a brand-new save (all four items, one
  each) and an "old save" (items added back once) are all the same. Warrior of Light and Cloud are unchanged. Battles
  (Reflect, Save the King, Crown Pendant, Trinity Limit) still work.
- **Menu speed:** these hooks only run when a list is built or the cursor moves, never on a still screen. The worst
  frame (opening the Shop's Buy list, the game checks every item for every character there: about 29,600 calls in one
  frame) costs the same as the reference disc within about 1 % (110-111 M vs 110 M CPU cycles; that frame is slow in
  the original game too). A first version was 1.7 % slower there; a shortcut in the module fixed it.
- Without the module (or without the registry) nothing hangs: Sora still has his items, but they do not grow with his
  level, Warrior of Light's □ panel lights Sora too (they share a bit), and the EX page shows Warrior of Light's face
  — the same "degraded" look the plan describes.

## 3. Registry decisions
- **Start-owned bit = bit 7 of the item_owner byte** (bits 0-5 owner 33..63, bit 6 must be 0). Source:
  `items.start_owned` (sora: 678-681). Why there: ENSURE / NEWGAME need "this item is given at the start" per item, the
  item_owner section is already per item and the header has no free field. `MIN_ENGINE` is now **0x00020400**: an older
  module would read 0x80 | owner as a foreign owner and silently lose every item effect, so it refuses the new file
  (reg_state −7, vanilla) instead. The frozen step-1..3 recipes keep their own frozen EXTRA.REG files. registry.py and
  the module refuse bit 6, an owner byte without a row and a start bit without an owner (module: REG_BAD_SECTION,
  first_bad 0xB0000 | index).
- **SCALE = aux kind 4** (`<HBB5H` entries: u16 item, u8 slot 0..3, u8 0, u16 points[5]; Sora: 678 slot 0 ATK 4/40/58/63/106,
  679 slot 2 HP 428/1882/2610/2610/6482, 680 slot 1 DEF 3/39/61/67/131, 681 slot 3 BRV 38/167/255/255/629 = R4's TAB).
  Needs ITEM_SCALING on the row and the item owned by that row (module checks; validator requires both ways). Module
  table 16 entries.
- **PICID = registry aux kind 3 EXPAGE** (u16 face_pic 15434, u16 name_pic 15435), **not** a P2.3 per-owner table.
  Why: (1) the mid-code hook has to stay anyway — the vanilla code computes base + owner − 1, a table cannot replace
  arithmetic without new code; (2) a P2.3 OXT table would need new EBOOT lookup code plus an owner bound in the stub
  fallback (EBOOT space and an allow-listed 0x21 immediate) for two values per owner; (3) rowgen has no EX-page picture
  table (D11 `ex_page_row` covers the text row; the two pictures are pack entries the installer appends), while the
  registry already carries per-owner picture ids (pic_slot, oq_face_pic …). The two EX-scene bases 15395 / 15363 are
  vanilla game constants and live in the module. Cost: without the module the EX page shows WoL's face (R4's
  documented degraded mode). Source: `behaviours.ex_page`.
- **`params.crown_drain` RETIRED** (coordinator decision, Q-S1 of P2.4-shield): the f32 at params +0x0C stays in the
  layout, is written 0, a source that sets it is refused (`RETIRED_PARAMS`), an old file decodes it as
  `retired_crown_drain`. HELM reads item_fx EX_DRAIN only (since step 2). Rule unchanged: an item's effect lives in
  item_fx, never in the row's params.
