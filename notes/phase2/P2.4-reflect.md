## In plain words (for Mat)
- Sora's EX Reflect (the guard that becomes the Reflega barrier in EX Mode and sends hits, HP attacks and spells back)
  and the Crown Pendant bonus were hand-written code stuck to the end of the battle file. They are C code in our
  module now. The battle file is back to exactly its original size.
- **The barrier itself is not code.** Its look (the KH2 Reflega shell, panels, flash, sound) is Sora's guard data,
  which this step does not touch. Only the "what happens when something hits the barrier" logic moved.
- An offline test runs the **old** reflect code in a tiny emulator next to the **new** C code on the same fake game
  data: every game call came out identical (C1, C2, C3, C7, Crown Pendant, + the C4 piece).
- On the emulator, side by side with the reference disc and the same scripted steps: Sora's EX guard sends melee hits,
  HP attacks and Lightning's spells back exactly like before (an HP attack costs the attacker HP equal to his own
  Bravery), Sora takes no damage through the EX guard, the Crown Pendant still makes EX Mode last ×1.3, Trinity Limit
  still works (4 of 4 full, incomplete ones land on the ground), and Cloud / Garland / Cloud's guard are unchanged.
- **The barrier looks the same**: frame-exact screenshots show the same Reflega shell, the same pop-in, white flash and
  fade on the same frames on both discs (the camera happened to sit on the other side, so the pictures are mirrored).
- Without the module (or without the registry) nothing hangs; Sora's EX guard is then just a normal guard.

Deliberate differences (all documented in the host test):
- **Owner test = registry**, not 33: C1/C3/C7/IS_SORA_EX use REFLECT_GUARD rows; C2 runs for REFLECT_GUARD | EE_GUARD rows;
  HELM for ITEM_EFFECTS rows with an EX_DRAIN item_fx row. R4's HELM had **no** owner test (any fighter with 681 in his
  loadout); only Sora can equip 681, so this differs only in an impossible state (host case "Crown on Cloud").
- **Overlay guard** for the two EBOOT hooks C1/C2: `battle_resident()` = the resident overlay's ELF header copy at
  0x089DD46C has p_vaddr 0x089DD4C0 and 0x185AB0 ≤ p_filesz ≤ 0x185CB0. Not resident → C1 keeps kind 4, C2 only the
  vanilla tail. (R4 lived in the overlay, so it never ran outside battle.)
- NULL checks where R4 would read through NULL (only with broken game state).
- Vectors handed to the game (C2 dir, C7 aim) live in 16-aligned module .bss (ENGINE.md §10), not on any stack.

## 5. Problems / lessons
- **Debugger polling can stop the game:** 8 back-to-back reads per poll ran the game at 0.6 logic frames/s (30 idle);
  CPU attacks looked "rare" because the game nearly stood still. ≤ 3 reads + 50 ms between polls keeps 30/s. Measure
  the frame counter (F+0x324) whenever a CPU seems passive.
- **CPU Minimal + TYPE Random hardly attacks**; TYPE Vicious (strength still Minimal) does. Reflect tests need an
  attacker with all three hit types: Lightning (Cloud gave no projectile at Sora's guard).
- A reflected HP attack costs the attacker HP = his Bravery: a Lv1 CPU with high Bravery is KO'd and the battle ends →
  cap the attacker's Bravery (assisted, both discs).
- **PPSSPP's debugger server wedged twice** (handshake times out, CLOSE-WAIT sockets pile up) while the game kept
  running; only a restart helped. Fewer, longer connections: `navseq.py` walks a whole menu in one connection.
- The CPU's input block (fighter+0x5A0 → 0x08C15CA0, source "virtual pad" 0x08C15BF0) does NOT drive the CPU's attacks
  when written (the AI acts elsewhere). Player 1's raw pad = 0x08C15B90 (PSP button bits), command bits 0x08C15C50.
- Wall-clock screenshots jitter by ~100 ms; frame-exact comparison = vblank breakpoints + window grab while halted
  (`gpu.buffer.screenshot` answers "Could not download output" while stepping). The camera orbit side is history-
  dependent, so identical fighter positions can still give mirrored framing.
- Setup screenshots matter: my first `boot_nav.sh` had 10 instead of 11 stage presses (Dream's End) — caught on the
  screenshot before any battle counted.
- The analyzer, not the live poll, should decide "damage while guarding" (the HP drop is often seen one poll after the
  guard motion already changed).
