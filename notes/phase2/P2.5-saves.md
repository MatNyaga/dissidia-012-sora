## In plain words (for Mat)
- Sora's saved progress (level, abilities, equipment) lives in the space of the 25th friend card. Before, five places
  in the game code said "fighter 33 → that card's space". Now one small rule decides it for every fighter pack:
  **the save slot is 57 minus the fighter number** (Sora 33 → slot 24, a second pack 34 → slot 23). The installer writes
  a tiny table ("which fighters have a save slot, and which version mark their record carries") into a piece of
  unused game code; no fighter number is written in the code any more.
- **Nothing changes for your saves.** The new code does exactly what the old code did, byte for byte: tested with
  copies of your saves on the emulator, side by side with the released version (records, Max. Level, battle counts,
  Original Quest "Sora Lv 42", friend cards, save → reload). It also works when our module is missing.
- **Found on the way:** your 100 % save file is still in the old pre-fix state (25 friend cards, Sora's record
  without its mark). The first time any Sora disc reads Sora's record it is fixed exactly like 1.0 does it (the list goes
  to 24, Sora keeps level 42). Nothing is lost; it was just never saved after the fix ran.
- **Adding a second pack later** costs one friend card: the oldest unlocked card is replaced (locked cards are never
  touched). Removing a pack again changes nothing; adding it back changes nothing. Packs can be listed in any order.
- The test fighter (owner 34) cannot be picked in menus yet, so its own record is tested in the host test, not on
  the emulator.

| **SRC1 block** EBOOT 0x089C2340-0x089C2508 (TRI-range tail after the XSTB v2 fallbacks; was clean dead-function words) | — | header `"SRC1"`, u8 REC_CAP, u8 36, u8 1, u8 0; REC_MARK u8[36] (+0x08); REC_FLAGS u8[36] (+0x2C, bit 0 LEGACY); PKG_REC 94 words (+0x50, to 0x089C2508) |
LOOKUP FUN_088CB3B4 stays R4's loop (no owner constant). Space: the 198 words 0x089C2028-0x089C2340 stay free for future
stub fallbacks (P2.7); the dead jump table (52 w) and the OXT spare (20 w) are untouched.

**PKG_REC(a0 = owner) → v0 = record or 0** (frame 0x20, keeps s0-s7 / ra; table loads only, no syscall):
1. `owner < 36` and `REC_MARK[owner] != 0`, else 0 (vanilla blank record, also every vanilla owner not in the list).
2. Migration, **once for all package slots**: `count > REC_CAP` → old = min(count, 25); count = REC_CAP (cut first); for
   i = cap .. old − 1: keep slot i if `rec[0] == 57 − i && 1 ≤ rec[1] ≤ 100 && (rec[0x777] ≠ 0 || REC_FLAGS[57 − i] & 1)`,
   else FUN_088f526c(list, card i) (the game's receive: the oldest unlocked card of 0..cap−1 is replaced, locked never)
   and then rec_i[0] = 0 ("needs set-up").
3. rec = list + (57 − owner)·0x10A8 + 0x10C; `rec[0] ≠ owner` → FUN_088cbbb4(rec, owner); `rec[0x777] ≠ MARK` →
   FUN_088cbd24(rec, 1, level), rec[0x777] = MARK.
With the Sora-only roster (REC_CAP 24, REC_MARK[33] 0xC1 + LEGACY) this is R4's SORA_REC for every input (host test).
Per call cost: package owners +~20 instructions vs R4 (table loads); the loop runs only while count > cap.

## 3. §A.3 pack-change behaviour — decisions (D) and what was tested
| situation | behaviour (built) | tested |
|---|---|---|
| 1.0 / R4 Sora save on a Sora-only disc | same code path and bytes as R4 | runtime A/B (incl. Mat's legacy 25-card state), host 944 cases |
| ≤ 23 cards, add pack 34 | nothing lost; 34's record set up at its first read | host (C2) |
| 24 cards (1.0 max), add pack 34 | count → 23; card 23 re-received over the oldest unlocked card (1 card lost) | **runtime** (scratch disc, card 8 replaced) + host |
| vanilla 25-card save, Sora + 34 | both package slots re-received in one go, records fresh when used | host (C4), runtime Sora-only variant (M1) |
| remove pack 34 (Sora stays) | cap back to 24, slot 23 a normal card slot; nothing changes at load | **runtime** (P25 after the t34 disc) |
| re-add pack 34 | slot 23 still a valid record → kept; else (card / zeroed) → fresh Lv1 | runtime (count ≤ cap: nothing changes) + host (C6) |
| remove Sora, keep 34 | cap 23; owner 33 → vanilla blank record; Sora's record in slot 24 untouched (a marked record counts as valid) | host (C7, C8) |
| reorder packs | identical bytes (slot from the owner number) | host (C9) |
- **D1** the record data is installer-written EBOOT data (SRC1), not REG_ROW: vanilla cost, offline-checkable, and save
  records keep working without EXTRA.PRX (a missing module must never reset or move a record). Runtime: module-missing
  and registry-missing saves = P25's byte for byte.
- **D2** REC_CAP is a data copy of the cap; installer writes cap words + REC_CAP from one value (code never reads the
  instruction word: PPSSPP's JIT may replace a block's first word with a marker).
- **D3** "valid record" = owner byte + level 1..100 + marker ≠ 0; the marker-0 exception (LEGACY) only for
  grandfathered packages. **D3a (edge, accepted):** with Sora removed (34 only), a pre-344c save (count 25, Sora's record
  without marker) would have slot 24 re-received as a "card" (garbage card) — only dev-era saves can be in that state.
- **D4** a migrated slot gets owner byte 0 right after the re-receive (R4 re-initialised it unconditionally; same
  bytes after set-up, and a stale owner byte can never pass as a record).
- **D5** count is clamped to 25 (R4 handled only slot 24 for any count ≥ 25).
- **D6 (finding)** "record stays until a card lands there" is not quite all: the Friend Card menu commit
  (FUN_088f7988, menu FUN_08a1da4c) re-initialises cards 0..cap−1, so a REMOVED pack's record (slot < new cap) is also
  cleared by the next Friend Card menu commit. Re-adding the pack then gives a fresh Lv1 record. Installed packs are
  never touched (their slots are ≥ cap).
- Owner-34 record set-up / catch-up cannot be reached in menus (no owner-34 fighter on the disc) → host only.
